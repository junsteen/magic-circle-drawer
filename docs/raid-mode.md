# 🛡 レイド魔法陣

## 概要

最大4人が同じルームに集まり、WebRTC で互いの筆をリアルタイムに共有しながら魔法陣を描くモードです。

現在実装されているのは **Phase 1（通信層）** のみで、「ルームに集まって、お互いの筆が見える」ところまでです。ボス戦・スコア集計・合体判定は Phase 2 で追加します。

設計の全体像（合体方式4種、ボス戦3形式、HP・ダメージ式、報酬設計）は Issue #182 に記録しています。

## 実装済みの範囲（Phase 1）

- ルーム作成と合言葉（6文字）による参加
- 参加URL・QRコードの共有
- 最大4人のフルメッシュ WebRTC 接続
- 相手の筆のリアルタイム表示
- 接続状態（接続中／接続済み／不安定／離脱）と往復遅延の表示
- 30秒つながらなかった場合の案内

## 未実装（Phase 2 以降）

ボス戦、合体方式の判定、スコア集計、AI僚機、報酬・アチーブメント、TURN サーバ、観戦、ホスト移譲、5人以上の参加。

## 画面

`/raid` からアクセスします。メニュー（☰）の「🛡 レイド魔法陣」からも開けます。

| 状態 | 表示 |
|---|---|
| 入室前 | 術士名の入力、ルーム作成ボタン、合言葉の入力欄 |
| 入室後 | 合言葉、QRコード（1人のとき）、キャンバス、参加者一覧 |

参加URLは `/raid?code=XXXXXX` の形式です。静的エクスポート（`output: 'export'`）と両立させるため、動的ルート（`/raid/[code]`）ではなくクエリパラメータを使っています。

## 通信の仕組み

### 全体の流れ

```
1. ルーム作成 → D1 に raid_rooms と raid_members を登録し、合言葉を発行
2. 参加      → 合言葉で raid_members に追加、既存メンバー一覧を取得
3. シグナリング → 1秒ごとに /api/raid/signal をポーリングし、SDP と ICE を交換
4. P2P 確立  → DataChannel が開通したらサーバを介さず直接やり取り
```

### 設計上もっとも重要な点

**リアルタイムの座標ストリームは演出専用で、採点には使いません。**

Phase 2 で採点を実装する際は、各プレイヤーがフェーズ終了時に完全な描画ログを一括送信し、ホストがそれを使って `calculateScore` を再計算します。これにより、パケットロスやジッタが採点結果に一切影響しません。座標ストリームは「相手の筆が動いて見える」ためだけに使うので、取りこぼしても演出が僅かに乱れるだけです。

この前提があるため、座標用の DataChannel は安心して unreliable モード（`ordered: false, maxRetransmits: 0`）で使えます。

### DataChannel は2本

| チャネル | 設定 | 用途 |
|---|---|---|
| `coords` | `ordered: false, maxRetransmits: 0` | 座標ストリーム。失っても支障がない |
| `control` | reliable | ハートビート、ストローク終端、離脱通知 |

ストロークの終端を取りこぼすと描線が繋がったままになるため、終端は reliable な `control` で送っています。

### 接続の張り方

4人フルメッシュで6接続です。双方が同時に offer を出す衝突（glare）を避けるため、**デバイスIDの辞書順で小さい側だけが offer を出す**というルールにしています。

シグナルはピアごとに直列処理します。offer の処理中に ICE candidate が割り込むと、待避と反映が入れ違って candidate を取りこぼすことがあるためです。`setRemoteDescription` より前に届いた candidate は `pendingCandidates` に溜め、あとでまとめて反映します。

## パラメータ

| 項目 | 値 | 根拠 |
|---|---|---|
| 上限人数 | 4人 | フルメッシュ6接続。8人だと28接続で非現実的 |
| 合言葉 | 大文字英数6文字 | 口頭で伝えられる長さ。31^6 ≈ 8.9億通り |
| ルーム有効期限 | 10分 | |
| 座標送信レート | 20Hz（50ms間隔） | 人間の筆致は5〜10Hz帯。60Hz送信は帯域4倍で見た目はほぼ同じ |
| 1メッセージの点数 | 最大8点 | |
| 間引き | 距離2px / 角度15度 | 直線は大きく削り、カーブは形を保つ |
| ジッタバッファ | 100ms | 相手の筆が0.1秒遅れても協力プレイでは支障がない |
| 帯域（4人時） | 上り下り 各約100kbps | |
| ハートビート | 2秒ごと | |
| 不安定と判定 | 6秒無応答 | |
| 離脱と判定 | 15秒無応答 | |
| RTT 警告 | 400ms超 | 表示のみ。判定はローカルなので不利益はない |
| 接続タイムアウト | 30秒 | 超過したら案内を表示 |
| ポーリング間隔 | 1秒 | |

STUN は Cloudflare と Google の2つを使います。対称NAT やモバイル回線では STUN だけでは繋がらないことがあり（経験則で8〜15%程度）、その場合は30秒で案内を出します。TURN の導入は Phase 3 の課題です。

## 描画（2層構成）

既存の単独プレイ（`useMagicCircle`）は毎フレーム全消し・全ストローク再描画をしていますが、4人分の筆を重ねるとこの方式では破綻します。レイドでは層を分けています。

| 層 | 更新頻度 | 内容 |
|---|---|---|
| 確定層 | ストローク完了時のみ | 描き終えたストローク。DOM に追加しないキャンバス |
| ライブ層 | 毎フレーム | 確定層を転写し、その上に進行中の筆だけを描く |

受信した点はジッタバッファぶん遅らせて表示し、Catmull-Rom スプラインを3次ベジェに変換して滑らかに繋いでいます。20Hz + 間引きで届く点は粗いため、直線で結ぶとカクつくためです。

自分の筆は遅延なしで即座に表示し、線を1px太くして他の参加者と区別します。

## サーバ側

Cloudflare Pages Functions + D1 です。既存のアカシックレコードと同じ `AKASHIC_DB` バインディングにテーブルを同居させています（新規 D1 を作ると `database_id` の払い出しが必要になるため）。

| エンドポイント | 内容 |
|---|---|
| `POST /api/raid/create` | ルーム作成。期限切れルームの掃除もここで行う |
| `POST /api/raid/join` | 参加。定員（4人）と期限をチェック。同一デバイスの再参加は定員に関係なく許可 |
| `POST /api/raid/signal` | シグナルの投函と受信、参加者一覧の取得を1回で行う |

テーブル定義は `migrations/0002_create_raid_rooms.sql` を参照してください。

マイグレーションの適用:

```
wrangler d1 execute akashic-record --file=migrations/0002_create_raid_rooms.sql
```

## 今後の拡張

- **Phase 2**: 合体方式4種（空間分割／レイヤー分割／シーケンシャル／同時同一）とボス戦3形式（タイムアタック／ライフ制／フェーズ制）。いずれもランダムに出す。合体方式はウェーブごと、ボス戦形式はレイドごとに抽選する
